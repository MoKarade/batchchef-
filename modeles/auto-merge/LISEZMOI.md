# Modèle commun de fusion automatique

Décision PURE « cette PR peut-elle être fusionnée toute seule ? », partagée par les apps de l'Atelier. Inspirée de `Hubperso/scripts/autoMerge.mjs` (décision testée, échec fermé, workflow lu depuis `main`). Le workflow n'est pas ici (étape B) : il récolte du JSON, appelle `decision`, puis obéit.

## Fichiers
- `autoMerge.mjs` : la décision et `peutArmer` (aucune dépendance, aucune I/O). `autoMerge.d.mts` : les types.
- `chemins-interdits-base.json` : la liste GÉNÉRIQUE des chemins jamais auto-fusionnés (voir règle 4), copiée dans les apps. `chemins-interdits-atelier.json` : la SURCOUCHE de l'Atelier (cockpit/*, tunnel), chargée en plus quand elle existe, jamais copiée dans une app.
- `armer.mjs` + `gabarit-armement.yml` : l'ARMEMENT de l'auto-fusion native (voir « Armement : le gabarit »). `verifier-copies.mjs` + `../manifeste.json` : vérification des copies (voir « Vérifier les copies »).
- `fusionner.mjs` : l'exécuteur du workflow (récolte via `gh`, appelle `peutArmer` puis `decision`, fusionne, commente, audite).
- `auto-merge.json` : exemple de configuration (à copier dans l'app, **lu sur `main`, jamais dans la PR**).
- `tests/autoMerge.test.mjs` : table d'attaque + cas nominaux. Lancer : `node --test modeles/auto-merge/tests/autoMerge.test.mjs` (Node 20+, sans dépendance).

## Principe
Le défaut est de NE PAS fusionner. Champ absent, état inconnu, lecture ratée, configuration invalide : refus. Un merge de trop part en production ; un merge raté se rattrape d'un clic.

## Règles codées dans le module (non désactivables par la configuration)
1. **SHA exact** : `pr.headRefOid` doit être égal à `contexte.shaAttendu` (le SHA de l'événement). Le workflow passe ensuite `decision.sha` à `gh pr merge --match-head-commit`.
2. **Échec fermé** : le contrôle REQUIS doit être vert ET publié par GitHub Actions (`appId` 15368, surchargeable par `app_id_requis` ; `fusionner.mjs` le lit via `check-runs`) : un check de même nom venant d'une autre application, ou ambigu, ne compte pas. Check absent, rouge, annulé, expiré ou en attente = refus ; aucun check = refus ; « sauté » n'est pas une preuve ; un ancien run rouge bloque même si le nouveau est vert.
3. **Branche du dépôt seulement** : `isCrossRepository` doit être `false` (champ absent = refus). Brouillon ignoré (`isDraft` doit être `false`).
4. **Jamais auto-fusionnés** : la liste est dans **`chemins-interdits-base.json` (générique) + `chemins-interdits-atelier.json` (surcouche de l'Atelier, absente des apps)**, chargés par `autoMerge.mjs` (imports JSON, aucune I/O au moment de la décision ; base ou surcouche illisible = échec fermé) : BASE (étroite, retour pole-architecture) : `**/scripts/hooks/**`, `.github/**`, `**/settings.json`, `.claude/settings*`, `**/commit-gate*`, `.claude/**`, `.husky/**`, `.claude/**`, `.husky/**`, `CODEOWNERS`, `.github/CODEOWNERS`, `modeles/**` (copies de modèles), `auto-merge.json`, `chemins-interdits.json` (et leurs variantes en sous-dossier), et, dans la SURCOUCHE de l'Atelier (qui ne perd rien de sa protection : `hooks/**`, `**/hooks/**`, `**/settings*`, `**/settings*/**`, `agence/settings-*.json`, `passerelle/tunnel.yml`), les fichiers qui commandent la sécurité du cockpit (`cockpit/tests/lancer.ps1`, `test_workflows.py`, `test_hygiene.py`, `cockpit/garde_hook.py`, `cockpit.py`, `evenements.py`, `flux_sse.py`, `bureau.py`, `.gitattributes`). La configuration du dépôt peut **ajouter** des chemins (`chemins_interdits`), jamais en retirer. Une PR qui en touche un : pas d'auto-fusion, `etiqueter: ["validation-marc"]`, et une raison lisible qui NOMME le chemin. Comparaison sans casse, séparateurs Windows acceptés, chemins normalisés ; chemin douteux (`..`, absolu, octet de contrôle) = refus ; un renommage compte l'ancien ET le nouveau chemin ; une suppression compte. Cette liste est **lue aussi par les agents git** : ils n'arment jamais l'auto-fusion sur une PR qui en touche un. Dépôts publics (plus tard) : CODEOWNERS + revue requise en plus ; dépôts privés : le contrôle du workflow.
5. **Labels** : `do-not-merge` bloque. `validation-marc` est INFORMATIF (il rend visible une PR qui attend l'attestation de pole-securite, il ne bloque plus : voir « Attestation de pole-securite »).
6. **Dependabot** : l'auteur doit être exactement `dependabot[bot]`, le **dernier push** aussi (un humain qui pousse dessus l'exclut), et la PR doit avoir au moins `carence_dependabot_jours` jours. Un login voisin (`dependabot-bot`…) est refusé.
7. **Arrêt d'urgence** : la variable `AUTOMERGE_OFF` (définie, hors vide et « 0 ») = aucune fusion.
8. **Contrôles non bloquants** : un check déclaré dans `controles_non_bloquants` (égalité stricte du nom) ne bloque pas, qu'il soit en attente ou rouge, mais n'est jamais une preuve. Cas d'usage : la revue d'agent Vercel de Hubperso (#83), lente et parfois en course. Tout autre check non vert reste bloquant.

## Armer l'auto-fusion : `peutArmer(pr, config)`
Le refus porte sur l'**armement** autant que sur la fusion. `peutArmer(pr, config)` → `{armer, raison, etiqueter}` : non si configuration invalide, brouillon, fork, label `do-not-merge` ou `validation-marc`, chemin interdit (source unique ou config) ou sensible, liste de fichiers douteuse. Elle ne regarde ni les checks, ni le SHA, ni la carence (cela ne concerne que la fusion : `decision`). Elle est appelée par `fusionner.mjs` **et** destinée aux workflows d'armement des autres dépôts (FinanceAI arme à l'ouverture de chaque PR) et aux agents git avant d'armer.
Quand le refus vient d'un chemin ou d'un label, `fusionner.mjs` écrit la **raison en commentaire de la PR, une seule fois** (marqueur caché `<!-- auto-merge-refus:… -->` : aucun doublon si le commentaire existe déjà ; une raison différente donne un nouveau commentaire), sans secret (texte nettoyé, borné, en code inline), pour que personne n'ait à deviner pourquoi elle ne part pas. Brouillons et forks : pas de commentaire.

## Configuration (`auto-merge.json`)
| Clé | Rôle |
|---|---|
| `controles_requis` | noms de checks qui doivent exister ET être verts (au moins un) |
| `controles_non_bloquants` | noms de checks ignorés (jamais un contrôle requis) |
| `chemins_interdits` | motifs en plus des règles fixes (refus, levé par l'attestation de pole-securite) |
| `chemins_label_validation` | chemins sensibles : refus + `decision.etiqueter = ["validation-marc"]` (label informatif) jusqu'à l'attestation de pole-securite |
| `securite_login` (option) | login GitHub du compte dédié de pole-securite (texte ; absent ou vide = AUCUNE attestation possible, les chemins sensibles restent bloqués) |
| `carence_dependabot_jours` | entier 0 à 60 |
| `branche_base` (option) | la PR doit viser cette base |

Motifs : `**` traverse les dossiers, `*` et `?` non. Une configuration invalide refuse tout.

## Ce que le workflow (étape B) doit fournir à `decision(pr, config, contexte)`
- `pr` : `gh pr view --json state,isDraft,isCrossRepository,labels,mergeStateStatus,baseRefName,headRefOid,statusCheckRollup,author,createdAt` (`checks` = `statusCheckRollup`, `auteur` = `author.login`, `creeLe` = `createdAt`), `fichiers` = liste de l'API `pulls/{n}/files` (avec `previous_filename` pour les renommages ; `gh pr view --json files` ne donne pas l'ancien chemin) et `dernierActeur` = qui a poussé le dernier commit.
- `config` : `auto-merge.json` lu sur `main`. Le workflow lui-même vient de `main` (`pull_request_target` / `workflow_run`), jamais de la PR.
- `contexte` : `shaAttendu` (SHA de l'événement), `env` (`{AUTOMERGE_OFF}`), `maintenant`.
- Après `merger: true` : `gh pr merge --squash --match-head-commit <sha>`. Si `etiqueter` n'est pas vide : poser ces labels.

## Attestation de pole-securite (spec : `docs/specs/attestation-revue.md`)
Décision de Marc (25/09) : sur les chemins sensibles, l'OK de pole-securite remplace son clic. Le signal est une revue **APPROVED** d'un compte GitHub DÉDIÉ (`securite_login`, lu sur la branche de base, jamais dans la PR) sur le **SHA exact** de la PR : les agents partagent tous le compte MoKarade, une étiquette ou une revue posée avec ce compte ne prouve rien.
- `attestationValide(reviews, {login, sha})` (pure, échec fermé) : revues du compte au login EXACT, la DERNIÈRE (`submitted_at`) décide ; valide seulement si `state === "APPROVED"` et `commit_id === sha`. DISMISSED, CHANGES_REQUESTED, COMMENTED, autre SHA, autre compte, login proche, liste illisible, date illisible, login absent = pas d'attestation. Les revues PENDING sont ignorées.
- `peutArmer` / `decision` : chemins de `chemins-interdits-*.json`, `chemins_interdits` et `chemins_label_validation` de l'app, test affaibli, test associé manquant : refus « attestation de pole-securite requise pour <SHA court> (…) » sans attestation ; avec elle, la suite normale. La PR porte les revues dans `pr.reviews`. Ne s'assouplit RIEN d'autre : brouillon, fork, contrôles requis (nom + application 15368), `do-not-merge`, frein horaire, SHA vérifié avant fusion (`--match-head-commit`), Dependabot, liste de fichiers douteuse.
- Lecture : `gh api --paginate repos/R/pulls/N/reviews` par `fusionner.mjs` et `armer.mjs` (`lireRevues`), seulement si `securite_login` est défini ; lecture ratée = `null` = aucune attestation (les PR non sensibles ne sont pas touchées).
- Déclencheurs : JAMAIS `pull_request_review` (il exécute la version du workflow venant de la PR). Après avoir approuvé, pole-securite lance le workflow de la BRANCHE PAR DÉFAUT : `gh workflow run armement-auto-merge.yml --ref <branche par défaut> -f pr=<numéro>` (gabarit d'armement, `armer.mjs` lit alors le SHA sur la PR ; le numéro est validé `^[1-9][0-9]{0,8}$`) ou `gh workflow run auto-merge.yml --ref main -f pr=<numéro>` (fusion). Le rattrapage planifié reste. Un lancement sur une autre branche ne fait rien (garde `github.ref`).
- **Toutes les catégories sont évaluées, un refus NON attestable l'emporte** (jamais « le premier refus gagne ») : une PR qui touche `.github/**` ET un `.env` reste refusée même avec une attestation valide. Non attestables : les `chemins_interdits` de l'app (secrets, migrations…), sauf ceux qu'elle déclare dans `chemins_attestables` (choix explicite, relu par pole-securite), et la liste `JAMAIS_ATTESTABLES` du modèle (`**/.env*`, `**/*.pem`, `**/secrets/**`, `**/jeton*`, `**/*.key`), jamais levée, même si l'app la déclare attestable. Attestables : `chemins-interdits-*.json`, `chemins_label_validation`, test affaibli, test associé manquant.
- `securite_user_id` (option, entier) : identifiant numérique du compte dédié, lu dans `user.id` des revues et exigé EN PLUS du login quand il est configuré (un login renommé puis réattribué à un autre compte ne compte pas). Recommandé dès que le compte existe.
- **Attestation par une GITHUB APP** (login `<slug>[bot]`, ex. `atelier-securite-marc[bot]`) : `securite_login` accepte le suffixe `[bot]` (comparaison EXACTE : le login humain de même préfixe n'est pas l'App, et inversement) ; `securite_user_id` devient OBLIGATOIRE (`gh api /users/<slug>[bot] --jq .id`, sans lui : configuration invalide et jamais d'attestation) ; la revue doit porter `user.type === "Bot"` et l'identifiant numérique attendu. L'App ne peut poser que des revues (permissions `pull_requests: write`, `contents: read`) : ni fusion, ni poussée. Les revues sont posées par `pc/scripts/attester-securite.mjs` (voir `docs/attestation-app.md`), jamais à la main.
- Un COMMENTED plus récent après APPROVED annule l'attestation (lecture stricte : la dernière revue du compte décide).
- Compte dédié : tant qu'il n'existe pas, `securite_login` est absent et les chemins sensibles restent BLOQUÉS (sûr). Point de grille : **A16** (`GRILLE-RELECTURE.md`).
- Dépôts publics avec protection de branche : en plus, CODEOWNERS des chemins sensibles = le compte dédié + revue des propriétaires requise + rejet des approbations périmées (double verrou natif, optionnel).

## Compensations : retrait des validations de Marc
Marc ne valide plus à la main tout le code exécuté sur le PC (`pc/**`, `agence/**`, `cockpit/**` passent seuls si les contrôles sont verts). En contrepartie :
- **Les tests des gardes sont protégés** comme les gardes (surcouche `chemins-interdits-atelier.json` : `test_hook.py`, `test_tache_ligne.py`, `test_securite_hook.py`, `test_activite.py`, `test_bureau.py`, `test_journal_rapports.py`, `test_local.py`).
- **Détecteur statique de « test affaibli »** (`testAffaibli`, sur le patch de `pulls/{n}/files`, aucun code exécuté) : pour les fichiers de tests (`**/tests/**`, `*.test.*`, `*.spec.*`, `test_*.py`, `*_test.py`), on signale un test supprimé ou déplacé hors des tests, un patch illisible sur un test modifié, un test qui perd plus de lignes d'assertion / `def test_` / `it(` / `test(` qu'il n'en gagne (une assertion triviale comme `assert True` n'en compte pas), ou un ajout de skip (`@unittest.skip`, `it.skip`, `xit`…). Effet : pas de fusion, `etiqueter: ["validation-marc"]` et une raison lisible qui nomme le fichier. **Le détecteur est un frein statique, pas une preuve** : remplacer une assertion par une autre plus faible (`assertEqual` → `assertTrue`, valeur attendue élargie) passe. Sauts détectés en plus : `@unittest.skip`, `expectedFailure`, `pytest.skip` / `importorskip`, `xit`, `it.skip`, `sys.exit(0)` / `exit(0)` / `os._exit(` / `process.exit(0)` (un module de test qui « réussit » sans rien exécuter) et `if False` ajoutés.
- **Test associé au code** (`regles_test_associe: [{code, test}]`) : du code qui change sans qu'un test associé PROUVE quelque chose demande la validation de Marc. Le test doit être **AJOUTÉ** (statut `added`) ou contenir au moins **une assertion AJOUTÉE** (une assertion triviale comme `assert True`, une modification neutre — commentaire, espace, renommage de variable —, un patch absent, un renommage sans contenu ou un test supprimé ne suffisent pas). Atelier : `cockpit/**` ↔ `cockpit/tests/**`.
- **Frein horaire** (`frein_fusions_par_heure`, 6 pour l'Atelier) : à partir de N fusions dans les 60 dernières minutes (lues sur GitHub, plus celles du passage en cours), la suivante est **refusée temporairement, SANS label** (un label `validation-marc` ne s'enlève pas tout seul : il reste réservé aux vrais motifs de sécurité) ; la PR est réexaminée au passage suivant et une alerte est émise. Compte illisible = PR sautée.
- **Alertes** : chaque fusion automatique laisse une ligne au résumé du job ET un commentaire sur la PR (une fois par SHA ; la raison y reste, en code inline). Toute ALERTE ou erreur ouvre une **issue `alerte-auto-merge`** bâtie UNIQUEMENT sur un **modèle fixe** : catégorie (`contrôle rouge à la fusion`, `frein horaire`, `test affaibli`, `test associé manquant`, `lecture impossible`, `fusion impossible`, `audit après fusion impossible`, `label non posé`, `commentaire non posé`), numéro de PR, SHA court, lien du run. **Jamais** un chemin, un nom de fichier ou un message d'erreur : ils viennent de la PR et pourraient injecter une @mention, un lien ou une fausse consigne vers le gérant et le cockpit. Une seule issue par signal tant qu'elle est ouverte ; le gérant et le cockpit la lisent avec `gh issue list --label alerte-auto-merge`. Le job doit avoir `issues: write`.
- **Preuve d'isolation avec persistance** : `isolation-runner.yml` pose des fichiers repères dans `_work`, `_work/_actions`, `_work/_tool`, TEMP et le profil, puis vérifie dans un second job que les quatre premiers ont disparu (le profil est seulement signalé).

## Armement : le gabarit (`gabarit-armement.yml`)
Certains dépôts (FinanceAI) ARMENT l'auto-fusion native de GitHub à l'ouverture de chaque PR. Le gabarit fait cet armement en respectant la grille de relecture sécurité (A1-A9) :
`pull_request_target` sans jamais récupérer le code de la PR (un seul checkout : la BASE), décision par API avec `peutArmer` lu sur la base (`armer.mjs`), types d'événements `opened, synchronize, reopened, ready_for_review, labeled, unlabeled, edited, converted_to_draft` (un label ou un brouillon DÉSARME), permissions `{}` globales et `contents` + `pull-requests` en écriture sur le seul job, actions épinglées par SHA, pas de fork, aucun texte de PR en entrée d'un `run:` ni d'une expression (numéro et SHA validés par expression régulière), ÉCHEC FERMÉ = désarmement (étape finale `if: failure()`), Dependabot jamais armé ici (l'auto-fusion native ignore la carence : ces PR restent au workflow de fusion). Runner : GitHub-hosted par défaut ; la variable de dépôt `ARMEMENT_RUNNER` (JSON) permet un runner auto-hébergé UNIQUEMENT si le dépôt est privé (garde `github.event.repository.private == true` : sur un dépôt public le job ne tourne pas). Arrêt d'urgence : `AUTOMERGE_OFF`.
`cockpit/tests/test_gabarit_armement.py` lit le gabarit comme DONNÉE (A10) et échoue si l'un de ces points disparaît ; le validateur est lui-même testé par mutation.

## Adopter le gabarit (une app)
1. **Copier** dans le dépôt de l'app : `modeles/auto-merge/{autoMerge.mjs, autoMerge.d.mts, chemins-interdits-base.json, fusionner.mjs, armer.mjs, verifier-copies.mjs, surblocage.mjs, LISEZMOI.md}` (mêmes chemins) et `gabarit-armement.yml` → `.github/workflows/armement-auto-merge.yml`. **Ne PAS copier** `chemins-interdits-atelier.json` (surcouche de l'Atelier : cockpit/*).
2. **Configuration par dépôt** : copier `auto-merge.json` en `.github/auto-merge.json` et l'adapter : `controles_requis` (le nom exact du job de CI), `chemins_interdits` (SURCOUCHE de l'app, s'ajoute à la base), `chemins_label_validation` (voir la liste suggérée), `carence_dependabot_jours`, `frein_fusions_par_heure`, `regles_test_associe` (`{code, test}` de l'app), `branche_base`. Base = liste générique fournie ; surcouche = ce que l'app ajoute ; la surcouche ne retire rien.
3. **Vérifier les copies** : `node modeles/auto-merge/verifier-copies.mjs .` (voir ci-dessous) doit répondre « Toutes les copies sont fidèles ».
4. **Réglages GitHub** : permissions par défaut du jeton en lecture seule, workflows de PR de forks désactivés, auto-fusion activée sur le dépôt, protection de la branche avec le contrôle requis, variable `AUTOMERGE_OFF` connue de l'équipe.
5. **Fichiers de l'app à protéger** : `.github/**` et `modeles/**` sont déjà dans la base ; ajouter à `chemins_interdits` les gardes propres à l'app (hooks, filtres, portes de test).
6. La PR qui ajoute le gabarit touche `.github/**` et `modeles/**` : elle demande la validation de Marc.

## Vérifier les copies
`modeles/manifeste.json` donne l'empreinte SHA-256 (fins de ligne ramenées à LF) de chaque fichier copiable. `node modeles/auto-merge/verifier-copies.mjs <dossier-du-depot>` compare, en LECTURE SEULE, un dépôt à ce manifeste : `OK`, `DIFFÉRENT` (copie modifiée à la main), `ABSENT`, `À NE PAS COPIER` (la surcouche de l'Atelier trouvée dans une app) ; code de sortie 1 au moindre écart. Dans l'Atelier, `--ecrire` régénère le manifeste après une modification du modèle (un test échoue tant que ce n'est pas fait). Les exemples (`auto-merge.json`) ne sont jamais comparés : ils s'adaptent par dépôt.

## Tester le sur-blocage
`node modeles/auto-merge/surblocage.mjs <dossier-du-depot> [--max N]` (lecture seule) applique la liste (base + surcouche éventuelle + `chemins_interdits` du dépôt) à `git ls-files` et affiche le nombre de fichiers bloqués, dont ceux de CODE APPLICATIF (hors `.github`, hooks de scripts, settings, config, modèle). Code 1 s'il y en a plus de N (défaut 15) : la liste est alors trop large pour ce dépôt (chez FinanceAI, `hooks/` = hooks React et `components/settings/**` = écran Réglages bloquaient ~35 fichiers d'UI). À lancer avant d'adopter le modèle et après chaque changement de la liste.

## COPIES.md (à la racine de chaque dépôt qui copie le modèle)
Tableau `chemin | SHA-256 (LF) | version du modèle`, une ligne par fichier copié : il atteste que les copies étaient fidèles à cette version. `node modeles/auto-merge/verifier-copies.mjs --ecrire-copies .` l'écrit dans le dépôt cible (refus si une copie n'est pas fidèle ; à lancer par le lot de CHAQUE dépôt, jamais dans l'Atelier) ; `verifier-copies.mjs .` le relit avec le manifeste : COPIES.md absent, périmé (version) ou en désaccord avec les fichiers = code 1. **Transition** : jusqu'à `copies_md_obligatoire_depuis` (manifeste, défaut 2026-10-15), un COPIES.md ABSENT n'est qu'un avertissement (« COPIES.md absent : obligatoire à partir du <date> », code 0) ; à partir de cette date c'est une erreur (code 1). Un COPIES.md PRÉSENT mais faux (empreinte, ligne en trop, version périmée) est toujours une erreur immédiate, de même qu'une copie de fichier altérée. Date absente ou illisible dans le manifeste : erreur (échec fermé). La version du modèle (`VERSION_MODELE`) est à incrémenter à chaque changement d'un fichier copiable.

## Volontairement absent
La neutralisation des échecs « quota » (Vercel) de Hubperso : elle suppose que la CI exécute déjà le build. Ici, un contrôle en échec ou en attente est un refus, sauf déclaration explicite dans `controles_non_bloquants`.

## Piste (non faite)
`gh` n'expose ni « qui a poussé » ni l'ancien nom des fichiers renommés (`gh pr view --json files`). Une fonction commune `lister_prs` (JSON complet d'une PR en un appel : fichiers avec `previous_filename`, dernier commit vérifié, checks) dans `agence/` éviterait de recoder cette récolte dans chaque workflow.
